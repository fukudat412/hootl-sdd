# 分解のルール

- 1タスクは1セッションで終わる大きさ（変更ファイル10以下が目安）。
- 受け入れ条件は、テストで確かめられる文で書く。「使いやすい」のような判定できない文は書かない。
- `paths` は主に変更するパスの glob。テストファイルのパスも含める。
- 先に土台（型・データ構造・共通処理）、後から画面。依存は `depends_on` で表す（すでにあるタスクにも依存してよい）。
- すでにあるタスクと同じことはしない。
- id は {next_id} から連番（すでにある id は使わない）。
- epic には今回の仕様の名前（{epic}）を入れる。
