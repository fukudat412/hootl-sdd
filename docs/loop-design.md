# ループ設計（決め打ち）

結論: **外側はキュー駆動（1タスク＝1セッション）、内側は「実装 → 機械判定 → 独立レビュー → 差し戻し」を最大3回**。人が入るのは「何を作るかを決める」と「朝のblocked確認」の2点だけ。仕様の凍結とタスクの取り込みは、人の承認ではなく機械の確認で進める（おまかせ）。

## 1. 検討したループの型と採否

| # | 型 | 中身 | 採否 | 理由 |
|---|---|---|---|---|
| A | 単一セッション長時間 | 大きな仕事を1セッションに渡して走らせる | 不採用 | 確認待ちで止まる／早めに「完了」と言う／コンテキストが埋まって迷走する |
| B | 同一プロンプト反復（Ralph型） | 同じ指示を延々と投げ直し、状態はファイルに残す | 部分採用 | 「状態をファイルに残す」だけ採用。何をやるかが曖昧なまま回るので本体には使わない |
| C | キュー駆動 | タスクを1件ずつ新しいセッションに渡す | **採用（外側）** | コンテキストが毎回まっさら。止まっても次の件に進める |
| D | 生成→判定→レビュー→修正 | 1タスクの中で直しを回す | **採用（内側）** | 「終わった」の判定をモデルから取り上げられる |
| E | 計画ループ | 仕様からタスクを補充し続ける | 採用（1回だけ） | 無人で計画し続けると発散する。計画は「人が決めた作りたいもの」1つにつき1回。承認は機械の確認に置き換え、エージェントが思いついた案はネタ帳に入れるだけで、自動では計画に回さない |
| F | 並列（worktree×N） | 独立タスクを同時に回す | **採用** | トークン消費と速度の両方に効く。マージだけ直列化 |

## 2. 全体の流れ

```
作りたいもの（人が書く／ネタ帳から選ぶ）
        │
        ▼
仕様の下書き（エージェント。決めきれない点は自分で決めて「自分で決めたこと」に残す）
        │  機械の確認: 「## やること」がある → specs/<日時>.md を main にコミット（凍結）
        ▼
spec ──(plan: エージェント)──▶ proposed-tasks.jsonl
                                       │  機械の確認: 形・id の重なり・行き先のない依存・依存の輪・件数
                                       │  通らなければ取り込まずに残す → 人が「計画と承認」で直す
                                       ▼
                              取り込み → SQLite キュー
                                       │
          ┌────────────────────────────┴───────── 並列 N 本 ─────┐
          ▼                                                      │
  [1] worktree を切る（task/<ID>）                                 │
  [2] 実装エージェント（Claude Code, headless）                    │
  [3] 自動コミット                                                │
  [4] 安全柵: 許可パス外の変更・テスト改ざん → 即差し戻し          │
  [5] ゲート: lint / typecheck / unit / e2e（全部コマンドの終了コード） │
  [6] 独立レビュー（Codex, 読み取り専用）→ verdict JSON             │
  [7] 全部通過 → main にマージ（ロックで直列化）→ done             │
      どこかで落ちた → 失敗内容を添えて [2] へ（最大3回）           │
      3回落ちた → blocked（理由を記録して次へ）                     │
          └──────────────────────────────────────────────────────┘
                                       ▼
                         朝のレポート（done / blocked / 消費 / ネタ帳に増えた案）
```

どの役（仕様・計画・実装・レビュー）も、途中で「今回は作らないが、よさそうな案」に気づいたら、出力に `::idea {"title": …, "body": …}` の1行を書く。ハーネスがそれを拾ってネタ帳（state.db の ideas）に入れる。ファイルを触らないので、読み取り専用のレビュー役でも書ける。ネタ帳はためるだけで、作るのは人が選んだ案だけ。

おまかせを切る（`hootl.toml` の `[auto] approve = false`）と、下書きとタスク案で止まり、人が読んで凍結・承認する元の流れになる。

## 3. 状態遷移

| 状態 | 意味 | 次 |
|---|---|---|
| `todo` | 着手可能（依存タスクが全部 done なら拾われる） | `running` |
| `running` | どれかのワーカーが処理中 | `done` / `todo`（再試行） / `blocked` |
| `done` | マージ済み | ― |
| `blocked` | 試行上限・マージ衝突・エージェント異常終了の連続 | 人が直して `hootl reset <ID>` → `todo` |

- 依存（`depends_on`）が blocked のタスクは拾われない。レポートに「巻き込まれ」として出る。
- `running` のままハーネスが落ちた場合、次回起動時に `todo` に戻す（ゾンビ回収）。

## 4. 判定の原則

1. **「完了」はモデルではなく終了コードで決める。** ゲートはすべて「コマンドが0で終わるか」。
2. **生成と検証を同じセッションでやらせない。** レビューは別ベンダー（Codex）で脱相関させる。
3. **安全柵はレビューより前。** 範囲外の変更はレビューに回す価値がない。
4. **差し戻しには材料を渡す。** ゲート出力の末尾・レビュー指摘を次の試行のプロンプトに入れる。
5. **詰まったら飛ばす。** 1件の詰まりで夜全体を止めない。
6. **承認は機械の確認に置き換え、通らないものだけ人に回す。** 人が読んでも見つけにくく、取り込むと気づかれないまま止まるもの（行き先のない依存・依存の輪・id の重なり）と、発散の兆し（件数）を見る。中身の良し悪しは、実装のゲートとレビューで決まる。
7. **何を作るかは人が決める。** エージェントの思いつきは仕様にもタスクにもせず、ネタ帳に入れる。無人で案を足し続けると、頼んでいないものが積み上がる。

## 5. Mandate > Cell > Run との対応

| mandale | このハーネス |
|---|---|
| Mandate | spec.md（凍結された仕様） |
| Cell | タスクの `epic`（機能のまとまり） |
| Run | タスクの1試行（`.hootl/runs/<ID>/<attempt>/`） |
| exit条件 | タスクの `acceptance` ＋ ゲート ＋ レビュー |

## 6. まだやらないこと

- ネタ帳の案を自動で作る（E を無人で回す）: 選ぶのは人のまま。案の質と量を見てから考える。
- 仕様・計画の独立レビュー（別ベンダーに読ませる）: 機械の確認で足りないと分かってから。
- レビュー結果による自動的なタスク分割: blocked の理由を見てから設計する。
- 本番デプロイ: 常に人がやる。
