# 開発標準（決め打ち）

無人で回すため、標準は「エージェントが守れる」かつ「機械で検査できる」ものだけにする。検査できない規約は書かない。

## 0. 原則: やれることは広く、判定は固く、被害は環境で閉じ込める

禁止を増やすほど、エージェントは迂回するか諦めるかになり、差し戻しと blocked が増えて人の手が戻ってくる。だから行動はできるだけ許し、守るのは次の2つだけにする。

| 守るもの | 理由 | 守り方 |
| --- | --- | --- |
| 判定の公正さ | 判定する側を触れると「合格」を作れてしまう | ゲート・lint・型・テスト・CI の設定と規約ファイルを保護、テストの無効化・削除を検出 |
| 被害の範囲 | 壊れても戻せる場所でだけ作業させる | worktree、毎回リセットするテスト用 DB、本番の秘密情報を渡さない、push はゲートとレビュー通過後にハーネスだけ |

依存の追加・スキーマ変更・タスクの想定範囲外の変更は許可する。代わりに理由を `docs/decisions/` に残させ、妥当性はレビュー役が判断する。

## 1. 仕様とタスク

- 仕様は全体の `spec.md` と、追加分の `specs/<日時>.md`（凍結済み）。仕様にないものは作らない。
- タスクは1件＝1セッションで終わる大きさにする。目安は「変更ファイル10以下、1〜2時間の人間作業相当」。
- 各タスクは必ず次を持つ。

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ○ | `T-001` 形式。ブランチ名・コミットに使う |
| `title` | ○ | 1行 |
| `description` | ○ | 何を作るか |
| `acceptance` | ○ | 受け入れ条件の配列。**テストで確かめられる文**で書く |
| `paths` | ○ | 主に変更するパス（glob）。範囲外の変更は `out_of_scope = "review"` ならレビューで判断、`"block"` なら差し戻し |
| `depends_on` | | 先に done になっている必要があるタスク |
| `epic` | | 機能のまとまり（Cell） |
| `priority` | | 小さいほど先。既定 100 |

## 2. ブランチとコミット

- 方式は trunk-based。`main` は常にゲートが通る状態。
- タスクごとに `task/<ID>` を worktree で切る。人もエージェントも `main` に直接コミットしない。
- コミットメッセージは `<type>(<ID>): <要約>`。type は `feat` / `fix` / `test` / `refactor` / `docs` / `chore`。ハーネスの自動コミットは `hootl(<ID>): attempt <n>`。
- マージは `--no-ff`。1タスク＝1マージコミットになり、戻しやすい。

## 3. 完了の定義（Definition of Done）

すべて機械判定。

1. 安全柵を通る（テスト改ざんなし・判定する側のファイル無変更）
2. ゲートがすべて終了コード0（lint / typecheck / unit / e2e）
3. 独立レビューの verdict が `pass`
4. `main` に衝突なくマージできる

## 4. テストの規約

- 受け入れ条件1つにつき、少なくとも1つのテストを書く。テスト名に受け入れ条件の番号を入れる（例: `T-012 AC2: 間違えた問題は翌日のキューに入る`）。
- 時刻・乱数は差し替え可能にする（`now()` と `random()` を注入する）。e2e で日付を固定するため。
- **禁止（安全柵が検出して差し戻す）**
  - テストの `skip` / `only` / `todo` の追加
  - 既存テストファイルの削除
  - ゲート設定・ハーネス設定・エージェント規約ファイルの変更

## 5. コード

- 可読性優先。賢い1行より、名前のついた3行。
- 決定論で済む処理はコードに書く。LLM を呼ぶのは判断点だけ。
- 依存の追加・スキーマ変更はしてよい。理由を `docs/decisions/` に1〜3行で残す。
- 迷ったら推測で埋めず、`docs/decisions/` に「判断不能: 〜」と書いてタスクを終える（レビューで差し戻され、blocked で人の目に入る）。

## 6. 設計判断の記録

- 標準や仕様から外れる判断は `docs/decisions/NNNN-<slug>.md`（ADR）に1件1ファイルで残す。
- 書式: 背景 / 決めたこと / 却下した案 / 影響。

## 7. 人の関わり方

| タイミング | 人がやること |
|---|---|
| 思いついたとき | 作りたいものを数行書く（管理画面の「仕様」→「おまかせで作る」、または `hootl auto --idea-file`）。仕様・計画・実装まで承認なしで進む |
| 朝 | `hootl report` の blocked だけ見る。直すか、タスクを割るか、捨てる。ネタ帳に増えた案を読み、作るものを選ぶ |
| 機械の確認で止まったとき | 「計画と承認」に残ったタスク案を直して取り込む（行き先のない依存・件数が多すぎる など） |
| 週1 | `main` を触ってみて、仕様を更新する |
